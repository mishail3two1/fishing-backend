## 0. Как общаться и работать

- Отвечай **на русском**. Идентификаторы в коде (классы, методы, таблицы, поля, эндпоинты) пиши **на английском**.
- Комментарии в коде короткие, на русском, только там, где неочевидно **почему** сделано так, а не что делает код.
- Автор проекта студент 3 курса, это курсовая работа. Он должен **понимать и уметь объяснить** каждую часть кода
  на защите. После каждой задачи кратко (5-10 строк) объясни, что и зачем сделано, и какие места самые важные.
  Не пиши «магический» код ради краткости.
- Перед задачей, которая затрагивает больше 3 файлов или меняет архитектуру/БД, **сначала дай план** и жди одобрения.
- Делай **маленькие шаги**: одна задача, одна ветка, один Pull Request. Не расширяй задачу без согласования.
- Если требование неясно, задай один конкретный вопрос вместо догадок.
- **Не выдумывай версии библиотек и API.** Если не уверен в версии или совместимости, проверь документацию
  или скажи, что не уверен.
- Если среда не позволяет что-то запустить (например, нет Docker), скажи об этом прямо. Не изображай,
  что тесты прошли, и не подделывай результат.

**Простота кода (автор должен понимать каждую строку, как если бы писал сам):**
- Пиши только то, что нужно для текущей задачи. Ничего «на будущее»: настройки, классы, зависимости
  и абстракции добавляются в той задаче, где они впервые используются.
- Предпочитай очевидный код короткому и хитрому. Интерфейс или общий класс заводи, только когда есть
  второе место использования (исключение: внешние сервисы за интерфейсами, см. раздел 4).
- Если Spring делает что-то неявно (автоконфигурация, аннотации, профили), назови это явно в объяснении
  и скажи, где это видно.
- В описании каждого PR есть раздел **«Как это работает»**: цепочка «что откуда вытекает» (например,
  запрос → контроллер → сервис → репозиторий → SQL) и 2-3 места, которые важнее всего для защиты.
- Если автор спрашивает «зачем эта строка?» и внятной причины нет, строку убираем.

## 1. О проекте

**Мобильное (PWA) приложение для рыбаков.** Бэкенд REST API для веб-клиента на React, который
устанавливается на телефон как PWA. Фронтенд пишет другой человек, у него отдельный репозиторий
(`fishing-frontend`). Бэкенд пишут двое студентов (блок A и блок Б).

**Главный пользовательский сценарий MVP:**
1. Пользователь открывает приложение и видит карту с водоёмами.
2. Выбирает водоём, открывается карточка: описание, платность, парковка, правила, какая рыба водится,
   текущие условия, последние уловы.
3. Добавляет свой улов: загружает фото, дата/геоточка/погода подтягиваются автоматически, вручную
   только рыба, вес, приманка, проводка (всё необязательное).
4. Смотрит свою историю уловов с фильтрами и поиском «что ловил здесь в это время в прошлом году».

**Гипотеза MVP:** если собрать актуальную информацию о водоёмах в одном месте (фауна, условия, последние
уловы), рыбак будет использовать приложение для выбора места перед выездом.

**Тип MVP: «Волшебник из страны Оз».** Пользователю кажется, что данные собираются автоматически, на деле
карточки водоёмов наполняются вручную (форумы, паблики, Telegram). Поэтому **автоматические парсеры писать
не нужно**. Нужны админские эндпоинты и импорт из CSV.

**Регион:** Челябинская область, начинаем с Челябинска и озёр вокруг него. Цель первых недель: 20-30 водоёмов.

**Метрики гипотезы** (пороги успеха/провала проверяет команда):
открытие карты ≥30% / <10%, просмотр карточки ≥50% / <20%, добавление улова ≥20% / <5%,
возврат к карте или истории ≥20% / <5%. Метрики считаются по **собственной таблице `events`**
(не по Google Analytics: законодательство РФ о персональных данных).

**Выводы из интервью, которые влияют на код:**
- Рыбаки не отдают точные координаты, потому что рыба не стоит на месте. Поэтому **улов приватный по умолчанию**,
  а точная точка улова никогда не отдаётся другим пользователям.
- Рыбалка не должна превращаться в работу: запись улова должна быть быстрой, всё необязательное опционально.
- На водоёме часто нет связи: API должен быть идемпотентным и безопасным для повторной отправки (uuid от клиента).

## 2. Команда и разделение работы

- **Блок A** (автор этого репозитория): каркас, БД и миграции, авторизация (JWT), водоёмы (карта, карточка, админ-CRUD,
  импорт CSV), деплой.
- **Блок Б** (напарник): улов и фото, погода, история и поиск, аналитика (события, агрегаты метрик).
- **Вместе:** распознавание рыбы (позже), контракт API, схема БД.
- Фронтенд (React) — третий человек, отдельный репозиторий. Бэкенд должен давать ему **стабильный, документированный API**.
- Изменение схемы БД или контракта API согласуется с обоими разработчиками. Не меняй чужой блок без явной просьбы.

## 3. Технологии и допущения

| Что | Решение |
|---|---|

| Сборка | **Maven**, используем Maven Wrapper (`./mvnw`) |
| Фреймворк | **Spring Boot 4.x** (последняя стабильная GA, не RC/SNAPSHOT) |

| Миграции | **Flyway**, схему создают только миграции |
| ORM | Spring Data JPA + Hibernate (+ `hibernate-spatial`, JTS) |
| Безопасность | Spring Security, JWT, BCrypt |
| Документация API | springdoc-openapi (Swagger UI). Версия должна быть совместима с Boot 4, проверь |
| Тесты | JUnit 5, Spring Boot Test, Testcontainers (Postgres+PostGIS), если Docker доступен |
| Прочее | Lombok (умеренно), Actuator, Validation |

**Принятые решения (команда может изменить, скажи об этом Claude):**
- groupId: `com.fishing`, artifactId: `backend`, name: `fishing-backend`, базовый пакет: `com.fishing.backend`.
  Пакет не переименовываем: Spring сканирует компоненты только внутри пакета главного класса,
  классы в другом пакете молча не подхватятся.
- Версии JDK и Spring Boot должны **совпадать у всех разработчиков**.

**Важно про Spring Boot 4:** по сравнению с 3.x изменились стартеры (более модульные) и пакеты некоторых
тестовых аннотаций. Не копируй импорты и конфигурацию из примеров для Boot 3.x вслепую, сверяйся
с документацией той версии, которая указана в `pom.xml`.

## 4. Архитектура и структура кода

Монолит: один Spring Boot сервис, одна Postgres, остальное внешние сервисы. Микросервисы не нужны.

Слои: `controller` → `service` → `repository`. Контроллер не содержит бизнес-логики, сервис не знает про HTTP,
сущности JPA наружу **не отдаются** (только DTO, лучше `record`).

Структура пакетов **по функциональным модулям** (package-by-feature):

```
com.fishing.backend
├── common/            исключения, обработка ошибок, общие DTO, утилиты
├── config/            SecurityConfig, OpenApiConfig, CORS, свойства
├── auth/              регистрация, вход, JWT
├── user/              пользователи
├── waterbody/         водоёмы, их рыба, админ-CRUD, импорт CSV
├── fish/              справочник видов рыб
├── catches/           уловы, поиск, история
├── photo/             загрузка и выдача фото, StorageService
├── weather/           клиент Open-Meteo + кэш
└── analytics/         события и агрегаты метрик
```

Внутри модуля: `XController`, `XService`, `XRepository`, `XEntity`, `dto/`. Имена классов в единственном числе.

**Сквозные правила:**
- Валидация входных DTO через Bean Validation (`@Valid`).
- **Единый формат ошибок:** RFC 7807 `ProblemDetail`. Глобальный `@RestControllerAdvice`. Не отдавай клиенту стектрейсы.
- Конфигурация через `application.yml` + профили (`dev`, `prod`), секреты **только из переменных окружения**.
- `spring.jpa.hibernate.ddl-auto=validate`: схему создаёт Flyway, Hibernate её не меняет.
- Транзакции на уровне сервиса (`@Transactional`), чтение `readOnly = true`.
- Внешние сервисы (погода, хранилище, в будущем ИИ) за **интерфейсами**, чтобы можно было подменить реализацию.
- Логируй осмысленно: без паролей, токенов и точных координат пользователей в логах.

## 5. База данных

Источник истины: `src/main/resources/db/migration/V1__init_schema.sql`. Прочитай его перед работой с БД.

Таблицы: `users`, `water_bodies`, `fish_species`, `water_body_fish`, `catches`, `catch_photos`, `events`.

**Соглашения, которые нужно соблюдать:**
- Координаты: SRID 4326, порядок **(долгота, широта)**: `ST_MakePoint(lon, lat)`. В JSON API отдаём явно `{"lat": ..., "lon": ...}`.
- Идентификаторы: `uuid` для данных пользователей (`users`, `catches`, `catch_photos`), клиент может прислать свой uuid
  при создании улова (идемпотентность при офлайн-отправке). `bigint` для справочников (`water_bodies`, `fish_species`) и `events`.
- Время только `timestamptz` (UTC), в API формат ISO-8601.
- Перечисления: `varchar` + CHECK, в Java `@Enumerated(EnumType.STRING)`.
- `catches.visibility` по умолчанию `PRIVATE`. `catches.deleted_at`: мягкое удаление, запросы по умолчанию его фильтруют.
- `catches.weather` и `events.properties`: `jsonb`.
- Запросы «водоёмы в видимой области карты» и «рядом»: PostGIS (`&&` с `ST_MakeEnvelope`, `ST_DWithin`), опирайся на GiST-индексы. Для них допустим нативный SQL.

**Правила Flyway (строго):**
- **Применённые миграции не редактируются.** Любое изменение это новый файл `V<N>__описание.sql`.
- Нумерация: перед созданием миграции сверься с открытыми ветками и Pull Request, чтобы номера двух разработчиков не совпали. Если конфликт, перенумеруй свою.
- Одна миграция делает одну логическую вещь. Данные справочников и водоёмов не зашивай в миграции, они загружаются импортом.
- Не используй `ddl-auto=update/create`.

## 6. Контракт API (черновик MVP, префикс `/api/v1`)

Меняется только по согласованию. Фронтенд строит интерфейс по OpenAPI, поэтому **любое изменение отражай в аннотациях springdoc**.

| Метод и путь | Назначение | Доступ | Блок |
|---|---|---|---|
| `POST /auth/register`, `POST /auth/login` | регистрация, вход, возвращает JWT | открыт | A |
| `GET /users/me` | профиль | пользователь | A |
| `GET /water-bodies?bbox=minLon,minLat,maxLon,maxLat` | лёгкий список для карты | открыт | A |
| `GET /water-bodies/{id}` | карточка: описание, рыба, условия, последние публичные уловы | открыт | A |
| `POST/PUT/DELETE /admin/water-bodies...` | админский CRUD водоёмов | ADMIN | A |
| `POST /admin/water-bodies/import` | импорт водоёмов из CSV | ADMIN | A |
| `GET /fish-species` | справочник рыб | открыт | A |
| `POST /catches` | создать улов (id можно прислать от клиента, повтор безопасен) | пользователь | Б |
| `POST /catches/{id}/photos` | загрузить фото (multipart) | владелец | Б |
| `GET /catches?waterBodyId=&speciesId=&bait=&season=&aroundDate=&windowDays=&page=&size=` | моя история и поиск «в это время в прошлом году» | пользователь | Б |
| `GET /catches/{id}`, `PATCH`, `DELETE` | один улов | владелец | Б |
| `GET /photos/{id}` | файл фото (проверка доступа) | см. приватность | Б |
| `POST /events` | событие аналитики | открыт (`session_id`) или пользователь | Б |
| `GET /admin/metrics/summary` | агрегаты под пороги успеха | ADMIN | Б |

**Решения по умолчанию (можно пересмотреть):**
- Чтение водоёмов и карточек открыто без входа (удобно посмотреть приложение и считать метрику «открытие карты»), всё остальное требует JWT.
- Пагинация: `page`, `size`, ответ со списком и общим количеством. Размер страницы ограничен сверху.
- Авторизация: заголовок `Authorization: Bearer <jwt>`. На MVP только access-токен с настраиваемым сроком
  (по умолчанию 7 дней: PWA часто офлайн), refresh-токены позже.
- CORS: разрешены только origin фронтенда из конфигурации.

## 7. Приватность и безопасность (обязательные правила)

- **Точные координаты улова другому пользователю не отдаются никогда.** На карточке водоёма публичные уловы показываются без `location`.
- Пароли только BCrypt. Никогда не логируем пароли, JWT и ключи.
- Проверка владельца на каждой операции с уловом/фото (пользователь не должен видеть и менять чужие приватные данные).
- Фото: ограничение размера (по умолчанию 5 МБ) и типа (`image/jpeg`, `image/png`, `image/webp`), проверка содержимого, а не только расширения.
  Дату и GPS читаем из EXIF при загрузке, а **публичную копию отдаём без EXIF-GPS**.
- Секреты (БД, JWT-ключ, ключи внешних API) только через переменные окружения. `.env` в `.gitignore`. Примеры в `.env.example` без реальных значений.
- Ключ внешнего ИИ-сервиса (на будущее) хранится только на сервере.
- Ограничивай размер запросов и частоту загрузок на уровне, разумном для MVP.

## 8. Фото, погода, аналитика (детали)

- **Фото:** на MVP хранение на диске сервера (путь из `STORAGE_PATH`, в Docker это volume) через интерфейс `StorageService`,
  чтобы позже заменить на S3. В БД только `storage_key`. Клиент сжимает фото до отправки, сервер всё равно валидирует.
- **Погода:** Open-Meteo (без ключа). Для прошлых дат архивный API, для текущих прогноз. Запросы с бэкенда, результат кэшируется.
  Снимок погоды сохраняется в `catches.weather` на момент создания улова. Падение погодного сервиса **не должно** ломать создание улова.
- **Аналитика:** типы событий `map_opened`, `water_body_viewed`, `catch_created`, `catch_history_viewed`. В `properties` нет персональных данных.
  Агрегаты считаются SQL по `events` в разрезе уникальных пользователей, знаменатель документируется.
- **Импорт водоёмов (CSV):** колонки `name,water_type,lat,lon,district,access_type,access_notes,has_parking,parking_notes,rules_notes,data_source`.
  Повторный импорт идемпотентен (по `slug`). Всегда заполняй `data_source`.

## 10. Git и процесс

- Ветка `master` всегда рабочая и защищена: только через Pull Request, прямые коммиты запрещены.
- Для каждой задачи короткая ветка от свежей `master`: `feature/<что>`, `fix/<что>`, `docs/<что>`.
- Коммиты небольшие и осмысленные, формат: `feat: добавить список водоёмов`, `fix: ...`, `docs: ...`, `refactor: ...`, `test: ...`.
- Pull Request маленький (идеально до нескольких сотен строк), с описанием: что сделано, как проверить, что не сделано.
- Не коммить `target/`, `.env`, файлы IDE, загруженные фото.
- Перед тем как считать задачу выполненной: сборка проходит, тесты проходят, миграции применяются на чистой БД, OpenAPI обновлён.
- Не делай `git push --force`, не переписывай историю, не удаляй ветки без просьбы.

## 11. Тесты

  фильтры истории, запрос водоёмов по области карты.

## 14. Формат работы с автором

- Код пишет автор, Claude даёт задание, каркас с `???` и подсказки по уровням (намёк → класс/метод → строка),
  затем делает ревью PR. Инфраструктуру, которую на курсовой не пишут с нуля (Security, JWT), Claude может
  предложить написать сам — по согласованию.
- Перед кодом: зачем задача, какие 2-3 новых понятия. Новые понятия объяснять на примерах из нашего кода.
- Задачи по шагам, по одному сообщению на шаг. После шага — проверка (запуск, тест, браузер).
- Проверять, что тест «умеет падать»: временно сломать и убедиться, что он красный.
- Среда автора: Windows, IntelliJ IDEA 2025.2, Docker Desktop, Maven Wrapper (`.\mvnw.cmd`).
  Частые проблемы и решения — в README.md («Частые проблемы»).
- Репозиторий `mishail3two1/fishing-backend` — форк. При создании PR проверять:
  base repository = `mishail3two1/fishing-backend`, base = `master`.
- Перед коммитом: `git status`, добавлять файлы явно (не `git add .`), убрать подсказки-комментарии из каркаса.
